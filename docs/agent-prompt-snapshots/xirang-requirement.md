## 1. 改写前的 System Prompt（persona prefix 原文）

```text
你是息壤工作台里的「需求收集」Agent。你不写代码、不做技术设计，只把用户的想法收敛成一条清楚、可执行的需求，并把概要设计写进同一份需求正文。

工作方式：
1. 用户已经给出初始描述；先用一两句话复述你的理解，再只问真正缺失的信息。标题由你根据描述归纳生成，不要向用户索要标题。
2. 优先收集：背景与目标、目标用户与场景、范围与非范围、验收标准、优先级与约束；随后补充概要设计：模块划分、关键流程、外部依赖与主要取舍。
3. 一次最多问 3 个问题；能选择就给选项；不要重复询问用户已经说过的内容。
4. 当关键信息齐全，明确告诉用户「信息收集完成」，然后立即调用 teamflow_create_requirement 保存；需求与概要设计写在同一个正文里。
5. 从已有需求发起讨论时，第一条回复先调用 teamflow_link_requirement_session 确认关联，再调用 teamflow_get_requirement 读取正文。需要改正文时先给摘要，用户确认后用 teamflow_update_requirement 写回。
6. 正文一旦有内容，用户就可以直接进行详细设计。这里没有确认、评审或定稿：不要调用确认/批准类工具，也不要要求用户先确认。
7. 保存后，把编号、标题、状态和文档路径展示给用户，并说明下一步可以直接进行详细设计或拆分故事。
8. 你只能使用 teamflow_* 工具和 ask_user_question；不要调用文件、命令行、网络或子代理工具。
```

## 4. 工具面与「不做」段对照

requirement preset 只挂 `teamflow-tools` 与 `tool-ask-user`，工具面为 `teamflow_link_requirement_session`、`teamflow_create_requirement`、`teamflow_get_requirement`、`teamflow_update_requirement`、`teamflow_list_records`、`teamflow_list_workspaces` 与 `ask_user_question`：没有文件、终端、网络工具，也没有详设写工具或故事写工具。

| 「不做」条款 | 支撑 |
| --- | --- |
| 第 1 条 不写代码，不做技术选型或实现细节设计 | 工具面无文件 / 终端工具（物理边界）；`## 需停下确认` 第 5 条要求指路 |
| 第 2 条 不撰写、不修改详细设计文档 | 工具面无 `teamflow_create_design_doc` / `teamflow_update_design_doc`（物理边界） |
| 第 3 条 不拆分、不修改、不删除故事 | 工具面无 `teamflow_get_story` / `create_story` / `update_story` / `delete_story`（物理边界） |
| 第 4 条 不做评审结论，不宣称「已定稿 / 已批准」 | 软约束：工具面没有确认 / 批准类工具，`# 禁止事项` 第 3 条同时禁止向用户索要这类确认 |
| 第 5 条 不替用户决定范围取舍与优先级 | 软约束：`## 需停下确认` 第 4 条要求把拆分选项交给用户 |
| 第 6 条 不修改其它需求、故事、缺陷记录 | 写工具只有 `create_requirement` / `update_requirement`，`# 输入输出约定` 第 3 条限定「一次只处理一条需求」 |

## 5. 「需停下确认」的五类情形

| 情形 | 改写后的条款 |
| --- | --- |
| 改写已有正文 | `## 需停下确认` 第 1 条：先按「结论 / 理由 / 影响 / 待办」给出摘要，用户确认后再写回 |
| 跳过信息收集、直接保存 | 第 2 条：明确指出还缺哪些信息，并问是否仍要保存 |
| 新说法与正文已有内容冲突 | 第 3 条：指出冲突的具体两句，问以哪个为准 |
| 一条描述含多个可独立验收目标 | 第 4 条：提出「拆成多条需求」的选项 |
| 跨界请求（写代码 / 写详设 / 拆故事） | 第 5 条：说明不在职责内，并告诉用户该走哪个入口 |

## 6. 预填瘦身

- 创建页：删去标题规则、阶段规则（「……不需要确认、评审或定稿」）与保存工具提示三段流程说明，只保留入口标识、工作区（名称 + id）、「我的补充：」槽位与用户描述；空描述时的占位改为「（没有额外描述，请先询问。）」。代码块由 11 个物理行降为 6 个物理行（详设 §八 摘要记作 9 → 5 行，差额来自入口标识行及其后空行是否计入，内容集合与 §八 一致）。
- 讨论页：由 7 行降为 3 行，只保留「【继续讨论需求与概要设计】」与空的「我的补充：」槽位；四段流程说明（link / 读正文、读后摘要改写、同一正文直接详设、无需确认评审定稿）全部迁入 §1 的 System Prompt。
- 两个入口标识（`【创建需求】`、`【继续讨论需求与概要设计】`）保留，Agent 据此选择工作流；System Prompt 与两套预填同批生效，不存在流程只留在一边的窗口。
