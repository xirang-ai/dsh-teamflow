## 4. 冲突与真空清单（AC3）

### C1（冲突，待用户决定）缺陷修没修好由谁判定

- 两句：
  1. bug `:236`「5. 不做验收结论：修没修好由用户与研发执行环节判定。」
  2. dev `:301` / `:317`「运行成功只代表「执行完毕」，不代表故事完成或缺陷已解决；完成由用户在页面上手动确认，你无法标记完成。」/「2. 不代替用户判定完成：不宣称故事完成、不宣称缺陷已解决。」
- 冲突点：bug 把「研发执行」列为判定方之一，dev 明确声明自己不判定；两个 Agent 都能读到这句，用户会看到互相矛盾的归口。
- 建议以 **dev 为准**：`finish_run` 只提交 `passed` / `failed` 与 summary，页面上的「完成 / 已解决」只能由用户点。bug 侧改法建议把 `:236` 改为「5. 不做验收结论：修没修好由用户在页面上确认。」（删去「与研发执行环节」）。
- 回改故事：**S3**（`sty_IxSTQUnTgQmXS3SLOyr_u`）。S6 不直接改。

### C2（缺口，待用户决定）story 没有「不做评审 / 定稿」条款

- 两句：
  1. requirement `:66`「4. 不做评审结论，不宣称需求「已定稿 / 已批准」——本工作台没有这个环节。」
  2. story 的 `## 不做`（`:148-154`）六条里没有对应的一句；story 区全文也没有「评审 / 定稿」字样。
- 缺口点：AC2 第 4 条要求「三个收集类 Agent 的『不做评审定稿』」逐项给出结论。按字面 requirement 有声、bug 以「不做验收结论」近似替代、story 完全无声——同一个工作台级立场在三个 Agent 上表述不齐。
- 建议以 **requirement / detail 的措辞为准**，在 story `## 不做` 末尾补一条：「7. 不做评审结论，不宣称故事「已通过评审 / 已定稿」——本工作台没有这个环节。」（bug 的「不做验收结论」可保留，二者不冲突，属同一立场的两种落点）。
- 回改故事：**S2**（`sty_itLjTnOXF-v8Hml8HV7Ih`）。

### C3（已解释的「真空」，无需回改）缺陷归属需求 / 故事

- 两句：bug `:234`「不判断缺陷应该归属哪条需求或哪个故事，也不声称已建立这类关联。」；requirement `:44`「不修改其它需求、故事、缺陷记录。」
- 表面看「谁都不管归属」，实际是产品边界：`src/store/model.ts` 的 `Bug` 接口只有 `id / title / body / severity / status / …`，没有需求或故事外键；bug profile 也没有 `link_requirement_session`。bug persona `:232`「缺陷是独立记录：不需要关联需求或故事，用户直接描述现象与预期就够了。」已把这个设计讲明。
- 结论：**不是真空，无需回改**；若产品将来要加归属，应先改数据模型与工具面，而不是改 Prompt。

### C4（接力设计，可选回改）「已知 / 待补」录入的缺陷会被研发执行再问一次

- 两句：bug `:224`「信息不足仍要录入时，正文分段写「已知」与「待补」，让后来人能看出还缺什么。」；dev 需停下确认 5「缺陷描述不足以定位时——用 ask_user_question 补充信息，不要猜测根因。」
- 判定：**不冲突**。前者是录入口径（先留下记录），后者是动手口径（定位不了就先问），两者都在保护「不猜根因」。
- 可选改进（低优先，需用户决定）：在 S4 的 `## 需停下确认` 第 5 条后加半句「缺陷正文里已标为『待补』的项，先向用户补齐再动手」，减少重复追问的观感。不回改也不影响一致性结论。

### C5（观察项，本次范围外）需求状态没有 Agent 入口

- 事实：`update_requirement` 参数只有 `id / title / summary / body`（`src/tools/update-requirement.ts:20-26`），没有 status；`archiveRequirement` 只是 store 方法（`src/store/workflow.ts:764`），五个 profile 都没有对应工具；需求 `completed` 由「故事全部 done」自动触发（`src/store/workflow.ts:1023`）。
- 影响：detail 需停下确认 3 问「需求已完成 / 已归档 / 已取消时是否继续设计」，但没有任何 Agent 能把需求置为归档。这是**既有机制**（状态由工作台流转 + 页面操作），不是本次 Prompt 改写的漏项。
- 结论：记为观察项，不在本轮回改；若要补，应作为独立故事改工具面。
